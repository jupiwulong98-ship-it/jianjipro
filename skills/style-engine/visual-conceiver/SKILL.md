# 画面构思

读取 Semantic Map、相邻口播上下文和 Style Profile 的视觉风格，输出 `references/style-engine/visual-concepts.schema.yaml`。这一阶段不读取卡片 catalog / registry，不输出 family、subtype 或 card_id。

策划前读取 [画面选择规则与参考案例](references/planning-rules.md)。它提炼用户提供的三份视频拆解报告，区分可迁移的解释方法与需要结合当前片子判断的节奏建议。参考案例用于推理，不作为关键词到固定效果的映射。

## 每段先作判断

1. **观众哪里容易不懂？** 写具体难点：看不出先后、混淆两个条件、找不到按钮、难以理解一变多等。没有额外理解任务时，可以保留人物。
2. **画面补充什么？** 说明位置、连接、运动或状态怎样解决这个难点。只写「丰富画面」「帮助理解」「用关系代替文字」不足以作出制作决定。
3. **最简单的表达是什么？** 先辨认关系，再考虑空间组织和变化。确实平级才用列表；输入输出、因果、复用、并行、演进不能只改写成若干条卡片。
4. **这一段放在整片里是否合适？** 看相邻内容、刚出现的构图、信息强弱与人物实际留白。连续同布局检查重复，强段之后考虑呼吸；保留人物同样写明理由。

将判断写进现有字段：`visual_focus` / `viewer_goal` 写具体要看懂的关系或操作；`visual_concept` / 开始、动作、结束字段写可观察的变化。工作台 `reason` 至少说清「难点：…；画面补充：…」，不能把同一句空泛理由复制给所有包装段。借鉴参考时可在内部 reason 注明案例编号及改动，成片不显示这些来源文字。

先回答「这句话最适合被观众看到成什么画面？」再描述主体、关系、出现顺序和最终落点。概念使用自然语言；`visual_structure` 是模板无关的关系标识，具体对象和箭头写进 `structure_description`。时间和 source_segment_ids 复用 Semantic Map，保留证据需求与主张状态。

只为值得包装的重要意群建立概念。其余保留干净口播；可以拆分一个意群或合并相邻意群，但不得改写口播或改变时间映射。`visual_focus` 说明观众要看懂的新认知，不能只写「丰富画面」。

关系示例（用于推理，不是关键词触发器）：
- 高 Star 不等于适合你：两侧对象、中间 ≠，结构 `not_equal`。
- 搜索、看介绍、复制链接：有操作顺序，结构 `sequence`，不能画成平级标签。
- GitHub 分享工具、资料和 Skill：仓库居中向外分支，结构 `center_branches`。
- 一次搭模板、以后换参数重复生成：母模板向多个产物复制，结构 `one_to_many`，不能退化成普通列表。
- 剪废话、字幕、补画面：在口播时间线上依次删除冗余、生成字幕轨、添加画面轨，结构 `input_process_output`。它是流程解释；声称实际软件操作时才必须索取真实录屏。

不凭元素数量决定结构。结构受控词表不限制创意：特殊关系用 `custom` 并说明关系，交由 Generated Motion；不要为命中词表修改概念。

`presentation` 允许 presenter_safe / full_screen / either；后续 Shotbook 落实具体模式和保护区。素材必需性与已就绪状态分开。素材缺失时，fallback 必须说明如何保留关系和解释性标签；真实证据不可用时明确阻断或回到干净口播，不能伪造证据。

截图用于展示真实证据或定位操作；抽象概念优先解释其关系。通用 B-roll 只有承担明确的对象、场景或结果信息时才使用，不能只为换画面而插入。解释性示意注明示意，不冒充实际操作或真实输出。截图先把网页链接、仓库地址和具体 Skill 名称写入像素遮盖，再做动画；成片不显示来源脚注或调试标签。

一个时刻保持一个主阅读焦点；复杂关系可以有多个节点，但应逐步展开和转移焦点。继承项目 Style Profile 的字体、配色和层级，不逐像素复制对标皮肤，也不因为参考的拍摄留白多而假定当前人物旁有同样空间。

## 交付前自查

- 画面明确解决了哪个理解问题？若只复述口播，改成关系表达、必要短强调或保留人物。
- 动作是不是推动新的关系、状态或观察焦点？单纯换标题、换颜色、换模板不能冒充信息推进。
- 复杂度是否超过信息收益？不能把简单三点做成高密卡墙，也不能用无数值依据的仪表盘伪造量化。
- 与前后段是否重复、是否有阅读和消化空间？参考报告中的秒数只作人工检查线索，沿用现有整片节奏 Gate，不增加固定频率的动画配额。
- 原文、字词锚点、真实素材需要、人物与字幕保护区是否一致？未看到实际画面时标待核对，不声称构图已经验证。

自查能解释策划选择，但不证明成片观感已经通过；还需稳定帧及实际播放审阅。发现文案本身缺少关系可记录建议，不擅自改写已剪好的口播。

输出经 `motion-library/scripts/style-contract.mjs` 验证后，再交 Edit Planner。Planner 和 Router 可反馈实现限制；修改概念要回到本层记录 revision_reason，Router 不可悄悄修改它。

新项目还需按 `docs/style-engine-v2/planning-workbench.md` 写入项目根目录 `visual-planning.json`。逐段记录观众目标、开始/结束画面、锚定剪后字词的动作、素材与理由；未包装段明确保留人物。按顺序覆盖全文，每个字词恰好引用一次，不按每条字幕机械生成效果。此文件是工作台审阅稿，不能当作已渲染的分镜图片；不选模板、不写 card_id。

工作台用表格直接并排展示原文与包装动作。确定关系后，可从 `motion-library/src/planning/rules.json` 关联 `packaging_rule`，让用户点击通用动态示意；保留人物用 `clean_presenter`。这是解释策划的预览标识，不是模板选择。无合适示意时省略字段、标待补，不为匹配示意改变概念；示意不能冒充该段成片、真实截图或精准字词同步。

把 `/#planning` 打开给用户查看，不能仅在聊天中展示构思。读取本轮 binding 对应的 planning-reviews 文件：未确认、存在未处理意见或来源版本变化时，先修改和复审，不进入模板制作。历史 visual-concepts 或旧 review.json 不代表本轮已确认。
